PL/SQL AI Data Flow Analysis System

This system analyzes large Oracle PL/SQL codebases using structured analysis instead of brute-force LLM processing.

  • Code scanning
  • Parsing
  • Knowledge graph
  • Vector search (RAG)
  • LLM orchestration

Problem

Enterprise logic is distributed across hundreds or thousands of files. A simple question like:

"What happens when an account is closed?"

…requires understanding tables, procedures, triggers, and documentation.

Sending everything to an LLM is:

  • Expensive
  • Slow
  • Inefficient

Architecture

Git Repository
     ↓
Code Scanner
     ↓
Parser
     ↓
Graph + Vector Database
     ↓
Local LLM Router
     ↓
Cloud Model
     ↓
Response

The system reduces token usage by sending only relevant context to the cloud model.

Step 1: Code Scanner

The scanner builds an inventory of everything in the repository.

Goal

Transform raw files into structured metadata:

{
  "file": "customer_pkg.sql",
  "type": "package",
  "name": "CUSTOMER_PKG"
}

Why It Exists

  • Reduces search space
  • Avoids sending entire repo to AI
  • Creates a reliable inventory

Key Stages

1. Repository Discovery

  • GitHub, Azure DevOps, Bitbucket
  • Collect .sql, .pkb, .pks, .pls

2. File Classification

  • Procedure
  • View
  • Package
  • Trigger

3. Extract Object Names

CREATE PROCEDURE UPDATE_CUSTOMER
→ UPDATE_CUSTOMER

4. Metadata Capture

  • Size
  • Line count
  • Last modified

5. Git Metadata

{
  "author": "jdoe",
  "commit": "abc123"
}

6. Documentation Linking

  • Associate .md files with code

7. Chunking

  • Break large packages into procedures

8. Object Registry

Central index of all objects:

CUSTOMER_PKG → /packages/customer_pkg.pkb

Outcome

  • Know what exists
  • Know where it lives
  • Know ownership and size

At this stage, the system is an inventory, not an understanding system.

Step 2: Parsing & Relationship Extraction

Step 2 turns the system from a catalog into an understanding engine.

Goal

Convert code into structured relationships:

UPDATE CUSTOMER
CALL send_notification;

Becomes:

{
  "object": "UPDATE_CUSTOMER",
  "writes": ["CUSTOMER"],
  "calls": ["SEND_NOTIFICATION"]
}

Why It Matters

Instead of searching text, you can ask structured questions:

  • What updates CUSTOMER?
  • What reads from CUSTOMER?
  • What calls this procedure?

Key Stages

1. AST (Abstract Syntax Tree)

Transforms code into structured meaning:

SELECT * FROM CUSTOMER
→ { "operation": "select", "table": "CUSTOMER" }

2. Read Relationships

READS → CUSTOMER

3. Write Relationships

WRITES → CUSTOMER

4. Procedure Calls

CALLS → SEND_NOTIFICATION

5. Package Structure

  • Package → contains procedures

6. View Dependencies

VIEW → DEPENDS_ON → TABLE

7. Trigger Analysis

TABLE → FIRES → TRIGGER

8. Job Execution

JOB → EXECUTES → PROCEDURE

Output Structure

Source           Relationship   Target
UPDATE_CUSTOMER  WRITES         CUSTOMER
UPDATE_CUSTOMER  CALLS          SEND_NOTIFICATION

Outcome

  • Understand data flow
  • Understand dependencies
  • Enable lineage analysis

This structured metadata becomes the foundation for the knowledge graph (Step 3).

Step 3: Knowledge Graph

Step 3 converts relationships into a navigable graph that enables impact analysis and lineage tracking.

Goal

Transform isolated relationships into connected data flow:

UPDATE_CUSTOMER → WRITES → CUSTOMER
CUSTOMER_REPORT → READS → CUSTOMER

Becomes a connected graph:

UPDATE_CUSTOMER
    ↓
  CUSTOMER
    ↑
CUSTOMER_REPORT

Why a Graph?

Traditional databases answer simple lookups well, but struggle with deep relationship traversal.

Graphs allow questions like:

  • What depends on CUSTOMER?
  • What breaks if I change this?
  • What is downstream from this table?

Key Concepts

Nodes (Entities)

  • Table
  • View
  • Procedure
  • Function
  • Package
  • Trigger
  • Job

Example:

(CUSTOMER:Table)
(UPDATE_CUSTOMER:Procedure)

Relationships (Edges)

  • READS
  • WRITES
  • CALLS
  • DEPENDS_ON
  • EXECUTES
  • FIRES

Example:

UPDATE_CUSTOMER → WRITES → CUSTOMER

Graph Construction

1. Load Nodes

Create a node for every object discovered in Step 2.

2. Load Relationships

Connect nodes using extracted relationships:

UPDATE_CUSTOMER → WRITES → CUSTOMER

3. Build Call Chains

PROC_A → PROC_B → PROC_C

Now you can answer:

  • What runs when PROC_A is executed?

4. Build Data Flow

CUSTOMER → CUSTOMER_VIEW → REPORT

5. Multi-Hop Traversal

The system can follow chains across multiple levels: 

CUSTOMER → VIEW → PROC → TABLE → REPORT

Capabilities

Impact Analysis

Question:

What breaks if CUSTOMER changes?

Result:

  • Dependent views
  • Procedures
  • Reports

Lineage Analysis

Trace data flow end-to-end:

ACCOUNT → BALANCE_VIEW → CALCULATION → REPORT

Dependency Queries

  • What writes to this table?
  • What reads from it?
  • What calls this procedure?

Ownership Mapping

Using metadata from Step 1:

  • Attach owners to nodes
  • Identify responsible teams

Example Query

Find everything impacted by CUSTOMER:

CUSTOMER
  ↓
VIEW_A
  ↓
PROC_B
  ↓
REPORT_C

Why This Reduces LLM Cost

Without the graph:

  • LLM searches entire repository

With the graph:

  • Graph finds relevant objects
  • LLM explains them

This drastically reduces token usage and improves accuracy.

Outcome

  • Impact analysis
  • Dependency tracking
  • Data lineage
  • Multi-hop traversal

At this stage, the system understands relationships and data flow.

Step 4: Semantic Layer (Embeddings + Vector Database)

Step 4 adds meaning-based search to the system. While the graph understands relationships, this layer understands intent and concepts.

Goal

Answer questions like:

"Where is customer onboarding handled?"

Even when those exact words do not appear in the code.

Why the Graph Isn’t Enough

The graph can answer:

  • What depends on CUSTOMER?
  • What calls UPDATE_CUSTOMER?

But it cannot answer:

  • Where is onboarding logic?
  • Find code related to failed payments

Because it only understands structure — not meaning.

Core Concept: Embeddings

Text is converted into vectors (numbers representing meaning): 

"Customer onboarding"
↓
[0.12, 0.93, 0.41, ...]

Similar meanings produce similar vectors, allowing semantic search.

Architecture Update

Repository
  ↓
Scanner
  ↓
Parser
  ↓
 ├── Graph (relationships)
 └── Vector DB (meaning)

Key Stages

1. Chunking (From Step 1)

Do not embed entire files.

  • CUSTOMER_PKG.GET_CUSTOMER
  • CUSTOMER_PKG.UPDATE_CUSTOMER

2. Semantic Summaries

Instead of raw code, generate meaningful descriptions:

Procedure UPDATE_CUSTOMER
- Updates customer status
- Writes audit history
- Sends notifications

3. Generate Embeddings

Convert summaries into vectors:

[0.234, 0.882, 0.121, ...]

4. Store in Vector Database

{
  "object": "UPDATE_CUSTOMER",
  "embedding": [...],
  "summary": "Updates status and sends notifications"
}

5. Semantic Search

Example query:

How is customer onboarding handled?

Returns:

  • CUSTOMER_SETUP_PKG
  • ACCOUNT_CREATION_PROC
  • Onboarding documentation

Hybrid Retrieval (Graph + Vector)

The most powerful approach combines both layers:

  • Graph → finds dependencies
  • Vector → finds meaning

Example:

Question: Explain balance calculations

Vector Search →
  BALANCE_PACKAGE
  Balance Docs

Graph Expansion →
  ACCOUNT → BALANCE_VIEW → REPORT

Combined context → Sent to LLM

Documentation Embeddings

Also index:

  • README files
  • Business rules
  • Wiki pages

These often provide better explanations than code.

Example Capability

Query:

What code handles failed payments?

Vector search finds:

  • PAYMENT_RETRY_PROC
  • PAYMENT_EXCEPTION_PKG

Graph expands dependencies:

PAYMENT_RETRY_PROC → NOTIFICATION_SERVICE

Why This Reduces Tokens

Without RAG:

  • Send entire repository to LLM (~100k+ tokens)

With RAG:

  • Send only 3–5 relevant objects (~2k–5k tokens)

Outcome

  • Search by meaning, not just names
  • Retrieve relevant code automatically
  • Combine with graph for full understanding
  • Significantly reduce LLM cost

At this stage, the system understands both:

  • Relationships (Graph)
  • Meaning (Vector search)

Step 5: Local Orchestration Layer (LLM Router)

Step 5 is where the system becomes intelligent about what to retrieve, how much context to send, and whether a cloud model is needed at all.

Goal

Decide what information is necessary to answer a question — and avoid unnecessary LLM usage.

Before vs After

Before Step 5

User Question
  ↓
Graph + Vector Retrieval
  ↓
Cloud Model (always used)

After Step 5

User Question
  ↓
Local LLM Router
  ↓
Decision:
  - Graph?
  - Vector?
  - Both?
  - Enough locally?
  - Need cloud?
  ↓
Compressed Context
  ↓
Cloud Model (only if needed)

Why This Matters

  • Reduces cost
  • Reduces latency
  • Avoids unnecessary cloud calls
  • Optimizes token usage

Core Concept: The Router

The local model doesn’t answer the question. It decides how to answer it. 

{
  "intent": "data_lineage",
  "use_graph": true,
  "use_vector": true,
  "use_cloud": false,
  "context_budget": 1200
}

Key Stages

1. Intent Classification

Understand what the user is asking:

"What updates CUSTOMER?"
→ impact analysis

"Explain balance calculations"
→ complex reasoning

2. Retrieval Strategy Selection

Choose which systems to use:

  • Graph only → dependency queries
  • Vector only → semantic search
  • Hybrid → complex questions

3. Context Budgeting

Limit how much data is sent:

Total Budget: 1500 tokens
- Graph: 300
- Vector: 800
- Summaries: 400

Prevents sending large amounts of unnecessary data.

4. Context Compression

Reduce raw output into structured summaries:

Before:
CUSTOMER_TABLE
UPDATE_CUSTOMER
CUSTOMER_VIEW

After:
{
  "entity": "CUSTOMER",
  "writes": ["UPDATE_CUSTOMER"],
  "reads": ["CUSTOMER_VIEW"]
}

5. Merge Graph + Vector Results

Combine structure and meaning into a clean context package: 

{
  "procedure": "UPDATE_CUSTOMER",
  "table": "CUSTOMER",
  "summary": "Handles onboarding and status updates",
  "dependencies": ["SEND_NOTIFICATION"]
}

6. Cloud Decision

Decide if a cloud LLM is needed:

  • Not needed: simple queries
  • Needed: reasoning + explanations

Examples (No Cloud):

  • What tables does this procedure write?
  • What calls this function?

Examples (Cloud Needed):

  • Explain the system architecture
  • Why is this logic inconsistent?

7. Prompt Construction

Build a compact prompt instead of sending full code:

User Question:
How is onboarding handled?

Graph Context:
- UPDATE_CUSTOMER → CUSTOMER

Vector Context:
- Onboarding logic documentation

Summary:
- Calls SEND_NOTIFICATION

8. Feedback Tracking

Track performance for optimization:

{
  "model_used": "cloud",
  "tokens": 2400,
  "could_be_local": true
}

9. Parallel Retrieval

Run graph and vector queries simultaneously:

Graph Query ┐
            ├ → Merge → LLM
Vector Query┘

Capabilities

  • Intent-aware query handling
  • Smart retrieval selection
  • Token optimization
  • Avoid unnecessary LLM calls
  • Automatic context compression

Why This Is a Turning Point

Before Step 5:

  • System retrieves data
  • Sends everything to LLM

After Step 5:

  • System decides what matters
  • Sends only relevant context
  • Sometimes skips LLM entirely

Outcome

  • Major cost reduction
  • Faster responses
  • Better accuracy
  • Scalable architecture

At this stage, the system becomes a true AI orchestration layer, not just a retrieval pipeline.

Step 6: Evaluation Layer (Telemetry + Model Benchmarking)

Step 6 transforms the system from an architecture into a measurable engineering platform. Every query becomes data that can be analyzed and optimized.

Goal

Measure and understand:

  • Cost (tokens, dollars)
  • Accuracy
  • Latency
  • Model performance

So instead of guessing:

"This model feels better"

You know:

"Model A is more accurate but 2x more expensive than Model B"

Architecture

User Query
  ↓
Step 5 Router
  ↓
Graph / Vector / Cloud
  ↓
Response
  ↓
Telemetry Collector
  ↓
Evaluation Engine
  ↓
Metrics Database

Key Stages

1. Log Every Interaction

Each request becomes structured data:

{
  "query": "How does onboarding work?",
  "intent": "data_lineage",
  "retrieval_used": ["graph", "vector"],
  "model_used": "cloud",
  "tokens_input": 3200,
  "tokens_output": 800,
  "latency_ms": 4200,
  "cost_usd": 0.018,
  "accepted": true
}

2. Model Performance Tracking

Measure performance per task type:

Task Type            Best Model
---------------------------------------
Graph Queries        Graph Only
PL/SQL Explanation   Cloud Model
Simple Retrieval     Local Model

3. Compare Models

Run the same query across multiple models and evaluate results: 

Model A → Accuracy: 9.1
Model B → Accuracy: 9.4
Model C → Accuracy: 8.7

4. Scoring System

Evaluate outputs using defined metrics:

  • Correctness
  • Completeness
  • Clarity
  • Dependency Accuracy
{
  "model": "Model A",
  "correctness": 9.5,
  "completeness": 9.0,
  "overall": 9.2
}

5. Token Efficiency

Track cost vs quality:

Model     Tokens   Score
------------------------
A         4200     9.1
B         1200     7.8

This helps determine the most efficient model.

6. Router Effectiveness

Evaluate if routing decisions were optimal:

{
  "router_decision": "cloud",
  "better_option": "graph_only",
  "cost_wasted": 0.012
}

7. Gold Dataset

Build a test suite of known questions:

  • What updates CUSTOMER.STATUS?
  • How does onboarding work?
  • Explain balance calculations

Use this to validate system accuracy over time.

8. A/B Testing

Split traffic between models:

50% → Model A
50% → Model B

Measure which performs better.

9. Detect Overuse

Identify unnecessary usage:

  • Too many cloud calls
  • Unneeded vector searches

Example insight:

70% queries → graph only sufficient

10. Cost Attribution

Break down cost by component:

Graph Query:   $0.002
Vector Search: $0.004
Cloud LLM:     $0.120
Total:         $0.126

11. Model Specialization

Identify strengths:

  • Graph → best for dependencies
  • Cloud → best for reasoning
  • Local → best for routing

12. Continuous Improvement Loop

Telemetry → Analysis → Optimization → Better Routing → Lower Cost

Capabilities

  • Data-driven model selection
  • Token cost optimization
  • Router performance improvement
  • Continuous system evaluation

Why This Matters

Without Step 6:

  • Decisions are based on intuition

With Step 6:

  • Decisions are based on data
  • Costs are measurable
  • Performance is provable

Outcome

  • Fully measurable system
  • Optimized model usage
  • Reduced costs
  • Improved accuracy over time

At this stage, the system becomes an AI observability platform, not just an AI pipeline.

Step 7: Self-Optimizing AI System (Closed Loop Learning)

Step 7 transforms the system into a self-improving platform that continuously learns how to reduce cost, improve accuracy, and optimize routing decisions automatically.

Goal

Move from:

  • Manual tuning
  • Static routing rules
  • Fixed prompts

To:

  • Automatic optimization
  • Adaptive routing
  • Self-improving prompts and strategies

Core Concept

Instead of engineers adjusting the system: 

Engineer → change rules → system improves

The system learns on its own: 

System observes → learns → updates itself → improves

Architecture

User Query
  ↓
Step 5 Router
  ↓
Graph / Vector / Cloud
  ↓
Response
  ↓
Telemetry (Step 6)
  ↓
Learning Engine (Step 7)
  ↓
Updated Routing + Prompts + Policies

Key Stages

1. Policy Learning

Each query becomes training data:

{
  "query": "How does onboarding work?",
  "router_decision": "cloud",
  "better_option": "graph + vector",
  "cost_wasted": 0.01
}

The system learns which decisions were optimal.

2. Router Self-Tuning

The router evolves based on historical performance: 

{
  "intent": "impact_analysis",
  "best_strategy": "graph_only",
  "confidence": 0.85
}

3. Automatic Prompt Optimization

The system improves prompts over time: 

Old Prompt:
Explain this procedure

Optimized Prompt:
Focus on:
- data flow
- dependencies
- side effects

4. Dynamic Context Sizing

Context size adapts to query complexity: 

Simple Query → 800 tokens
Medium Query → 2000 tokens
Complex Query → 6000 tokens

5. Graph Expansion Learning

The system learns how far to traverse the graph:

  • Customer queries → 3 hops
  • Billing flows → 7 hops

Reducing unnecessary data and tokens.

6. Retrieval Strategy Optimization

Determines when to use each layer:

  • Graph only
  • Vector only
  • Hybrid
  • Cached answer

7. Intelligent Caching

Store responses for repeated queries: 

{
  "query_signature": "hash123",
  "answer": "...",
  "valid_until": "code changes"
}

Avoids repeated computation entirely.

8. Drift Detection

Detect when code changes invalidate knowledge:

  • Invalidate cache
  • Update graph
  • Re-evaluate strategies

9. Automatic Model Selection

Choose the best model dynamically: 

{
  "task": "lineage_analysis",
  "best_model": "cloud",
  "confidence": 0.91
}

Or skip LLM entirely: 

{
  "task": "simple_query",
  "best_model": "graph_only"
}

10. Feedback Integration

Learn from user behavior: 

{
  "accepted": false,
  "issue": "missing_dependency"
}

System adjusts future behavior accordingly.

11. Self-Generated Training Data

System creates its own improvement dataset: 

Query → Retrieval → Response → Evaluation → Improved Answer

12. Continuous Optimization Loop

Observe
  ↓
Evaluate
  ↓
Optimize
  ↓
Deploy changes
  ↓
Repeat

Capabilities

  • Self-optimizing routing decisions
  • Automatic prompt tuning
  • Adaptive context management
  • Dynamic model selection
  • Intelligent caching

Why This Matters

Before Step 7:

  • Engineers manually tune system
  • Improvements are slow

After Step 7:

  • System improves automatically
  • Cost decreases over time
  • Accuracy increases continuously

Outcome

  • Self-learning AI system
  • Continuously improving performance
  • Reduced operational overhead
  • Enterprise-grade optimization engine

At this stage, the system is no longer just a pipeline. It becomes a learning optimization platform for enterprise knowledge systems.
